# 02 · RAG и базы знаний

## Q1. Что такое RAG и зачем он нужен ассистенту банка?

**Короткий ответ:** RAG — Retrieval-Augmented Generation. Перед генерацией ответа мы ищем релевантные фрагменты в базе знаний и подаём их в контекст LLM. Для банка это критично: ответы должны быть **основаны на актуальных регламентах**, а не на «памяти» модели, которая может быть устаревшей или галлюцинировать.

**Ключевые свойства правильного RAG для банка:**

- **Grounded** — каждый ответ ссылается на источник.
- **Fresh** — знания обновляются, устаревшие документы помечаются.
- **Auditable** — можно показать, какой документ модель «увидела» в момент ответа.
- **Bounded** — если в KB нет ответа, ассистент явно говорит «не знаю», а не выдумывает.

## Q2. Архитектура RAG-пайплайна — что обязательно?

```
[Источники: Confluence, регламенты, FAQ, Jira, БД]
        │
        ▼
[Ingestion: парсинг, нормализация, чистка]
        │
        ▼
[Chunking: разбиение с перекрытием + метаданные]
        │
        ▼
[Embedding: векторизация чанков]
        │
        ▼
[Storage: vector DB + lexical index + metadata store]
        │
        ▼
[Query time: hybrid retrieval → rerank → top-k]
        │
        ▼
[Generation: LLM с контекстом + цитаты]
        │
        ▼
[Eval: faithfulness, retrieval recall, answer quality]
```

## Q3. Как делать chunking?

**Подход:**

- **Семантический chunking**: режу по структуре документа (заголовки, разделы), а не «по 500 токенов».
- **Размер**: 200–800 токенов на чанк, в зависимости от природы документа. Для регламентов лучше крупнее — не разрывать смысл.
- **Overlap**: 10–20% перекрытия — чтобы пограничные предложения не теряли контекст.
- **Метаданные** на чанке: `doc_id`, `title`, `section`, `version`, `effective_date`, `expiry_date`, `audience` (бухгалтер / селлер), `confidentiality`.
- **Иерархия**: храню и краткое summary документа, и chunks — для двухуровневого retrieval (сначала найти документ, потом раздел).

**Антипаттерн:** просто `split(text, 512)` без учёта структуры. Это ломает таблицы, формулы и ссылки.

## Q4. Hybrid search — что это и зачем?

**Hybrid = vector search + lexical (BM25/keyword) search + reranker.**

- **Vector** хорошо ловит **смысловую близость** («как заплатить налог за квартал» ≈ «оплата налогов поквартально»).
- **Lexical (BM25)** хорошо ловит **точные термины, коды, номера документов** («НДС-2», «172-ФЗ»). Это критично в банке — клиенты часто пишут точное название регламента.
- **Reranker** (cross-encoder, например `bge-reranker`, `cohere-rerank`) переупорядочивает top-N кандидатов с учётом запроса в паре с чанком — повышает precision.

**Типичный flow:** vector top-50 ∪ BM25 top-50 → dedup → rerank → top-5 в контекст.

## Q5. Как ловить «retrieved but wrong» и «model guessed not from KB»?

Это два разных класса ошибок. Каждый требует своего сигнала.

**Retrieved but wrong (плохой retrieval):**
- Метрика **retrieval recall@k** на golden set: для эталонных вопросов знаем правильный документ — проверяем, попал ли он в top-k.
- Метрика **context precision**: какая доля чанков в контексте действительно релевантна.
- Сигнал в проде: low-confidence ответ + thumb-down → ручной разбор.

**Model guessed (галлюцинация без оснований):**
- Метрика **faithfulness / groundedness**: автоматически проверяем, что каждое утверждение в ответе подтверждается контекстом (LLM-as-judge или NLI-модель).
- Промпт содержит явное правило: «Не отвечай ничего, что не подтверждено в `<knowledge_base_snippet>`. Если нет — верни refusal».
- Структурированный вывод с обязательным полем `citations[]`: ответ без цитат = блокируется на уровне валидатора.

## Q6. Как обновлять базу знаний и не подмешивать устаревшие регламенты?

**Принципы:**

- **Версионирование документов**: у каждого чанка `effective_date` и `expiry_date`. Retrieval фильтрует устаревшие.
- **Source of truth**: фиксируем, кто owner каждого документа, кто подписывает обновление.
- **Pipeline ingestion**: webhook от Confluence/CMS → парсинг → diff → переэмбеддинг изменённых чанков → атомарная замена в индексе.
- **Soft delete + archive**: устаревшие чанки не удаляем сразу, помечаем `archived=true` с датой, чтобы можно было ответить на вопрос «как было».
- **Тесты на freshness**: golden set содержит вопросы, ответы на которые меняются по дате. Регулярный прогон проверяет, что модель отдаёт актуальную версию.
- **Алерт**: «retrieval вернул чанк с `expiry_date < today`» → инцидент.

## Q7. Эмбеддинги — какие выбирать?

**Критерии выбора:**

- **Язык**: для русскоязычной банковской базы — модели с русским в обучении (`bge-m3`, `e5-mistral-7b-instruct`, `paraphrase-multilingual`, `intfloat/multilingual-e5-large`, российские `cointegrated/rubert-tiny2` для лёгких задач).
- **Размерность vs стоимость**: 1024–1536 — рабочий баланс; больше — дороже хранение и поиск.
- **Domain fit**: если есть бюджет и данные — fine-tune или хотя бы prompt-tuning эмбеддера на банковской лексике.
- **Privacy**: для банка предпочтение — **on-prem эмбеддеры**, чтобы документы не уходили в публичный API.

## Q8. Какую vector DB выбрать?

**Критерии:**

- **Hybrid поддержка** (vector + BM25): `Qdrant`, `Weaviate`, `OpenSearch`, `Elastic`, `pgvector + tsvector`.
- **Метаданные и фильтры**: возможность фильтровать по `effective_date`, `audience`, `confidentiality`.
- **On-prem deployment**: для банка обычно требование.
- **Масштаб и стоимость**: если миллионы чанков — Qdrant/Weaviate; если десятки тысяч — `pgvector` достаточно и проще в эксплуатации.

**Мой ответ на интервью:** не привязан к конкретной БД, выбор зависит от объёма, требований к hybrid и инфры команды. Опыт с Postgres и продакшен-эксплуатацией — есть, `pgvector` для старта вполне рабочий.

## Q9. Что делать, когда документов нет, а вопрос валидный?

- Явный **refusal с эскалацией**: «Не нашёл точного ответа в базе знаний, передаю запрос специалисту».
- Логирование `unanswered_query` → попадает в backlog content team.
- Если категория вопросов повторяется — сигнал расширить KB.

## Q10. Многоязычность и термины

В банковской KB часто смешан русский, английский (термины), коды документов. Подходы:
- Эмбеддер мультиязычный.
- В chunking сохраняем оригинальные термины (не переводим).
- В промпте разрешаем модели использовать английские термины, если они есть в источнике.

## Шпаргалка ошибок RAG

| Ошибка | Причина | Лечение |
|--------|---------|---------|
| Ответ верный, но без источника | Промпт не требует citations | Сделать citations обязательным полем |
| Ответ неверный, но из KB | Плохой chunking, потерян контекст | Семантический chunking, overlap |
| Ответ выдуман | Слабый retrieval, нет refusal-политики | Hybrid + reranker + явный refusal |
| Ответ устарел | KB не фильтрует expired | Метаданные `effective_date` + фильтр |
| Низкий recall на коды/номера | Только vector | Добавить BM25 |
| Контекст-окно переполнено | Слишком много chunks | Reranker + top-k=3..5 |
| Утечка чужих данных | Нет access control в retrieval | Фильтр по `audience` / `tenant_id` |

## Шпаргалка терминов

| Термин | Краткое определение |
|--------|---------------------|
| RAG | Retrieval-Augmented Generation |
| Chunk | Фрагмент документа для индексации |
| Embedding | Векторное представление текста |
| Vector DB | БД для поиска по эмбеддингам |
| Hybrid search | Vector + BM25/keyword |
| Reranker | Модель для переупорядочивания результатов поиска |
| Recall@k | Доля случаев, когда правильный документ в top-k |
| Faithfulness | Соответствие ответа контексту (отсутствие галлюцинаций) |
| Grounding | Привязка ответа к источникам |
