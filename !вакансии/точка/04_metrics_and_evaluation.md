# 04 · Метрики и оценка LLM-систем

## Q1. Какие метрики качества вы используете для диалогового ассистента?

**Я делю метрики на четыре уровня:**

### 1. Retrieval (если есть RAG)
- **Recall@k** — попал ли правильный документ в top-k.
- **MRR / NDCG** — где именно он стоит.
- **Context precision** — какая доля чанков в контексте релевантна.

### 2. Generation
- **Faithfulness / groundedness** — все утверждения подтверждены контекстом (LLM-as-judge или NLI).
- **Answer relevance** — отвечает ли ответ на вопрос.
- **Completeness** — не упущены ли важные детали.
- **Citation accuracy** — правильные ли источники указаны.

### 3. Безопасность и политика
- **Refusal rate** — доля отказов; должна быть в адекватном диапазоне (низкая = модель отвечает на лишнее, высокая = бесполезный ассистент).
- **Policy violation rate** — нарушения brand voice, утечки PII, темы вне scope.
- **Adversarial robustness** — устойчивость к prompt injection и jailbreak (отдельный набор).

### 4. Продуктовые / бизнес
- **Resolution rate** — доля диалогов без эскалации к человеку.
- **CSAT / thumb-up rate**.
- **Repeat question rate** — клиент спросил то же самое заново (proxy для непонятого ответа).
- **Time to answer** (p50/p95).
- **Cost per resolved ticket**.

## Q2. Offline vs online evaluation

**Offline (до выкатки):**
- Прогон на golden set (50–500+ кейсов).
- Adversarial set.
- Сравнение с baseline (предыдущая версия промпта/модели).
- Регрессионные пороги: «ни одна метрика не упала больше чем на X%».

**Online (после выкатки):**
- A/B на 1–10% трафика, метрики продуктовые + LLM-as-judge на сэмпле.
- Стоп-критерии: рост policy_violation_rate, рост escalation_rate.
- Алерты на дрейф (изменение распределения тем, длины ответов, refusal).

## Q3. LLM-as-judge — как сделать правильно?

**Подход:**

1. **Чёткие критерии** — судье дают rubric: что считаем «correct», «incomplete», «wrong». Без рубрики оценки шумные.
2. **Pairwise лучше скалярных оценок**: «A лучше B, B лучше A или ничья» — даёт стабильнее результат, чем «оцени от 1 до 5».
3. **Калибровка** — 50–100 кейсов размечает человек, потом считаем согласие с судьёй (`Cohen's kappa`, `agreement rate`). Если согласие < 0.6 — рубрика плохая, переделываем.
4. **Reference judge**: для banking-домена иногда нужен судья **с доступом к KB**, чтобы оценивать faithfulness.
5. **Self-bias**: не использую модель как судью её же ответов — берём другую модель или другую версию.
6. **Human spot-check**: 5–10% выборки всегда проходит ручную разметку для контроля.

**Антипаттерн:** «попросил GPT оценить ответ от 1 до 10» без rubric и калибровки. Это шум.

## Q4. Что такое golden set и как его собрать?

**Структура:**

- 50–500 пар `(question, expected_behavior)`.
- Категории: типичные интенты (60%), edge cases (20%), adversarial (10%), ambiguous (10%).
- Каждый кейс размечен: ожидаемый ответ или критерий правильности (если ответов много — нужны критерии, не точный текст).
- Для RAG: явно указан правильный документ-источник.
- Метаданные: `category`, `difficulty`, `priority`, `audience` (бухгалтер / селлер).

**Источники:**

- Логи реальных диалогов (с маскированием PII).
- Эскалации к операторам.
- FAQ.
- Сценарии от продукта.
- Adversarial — собирать отдельно (red team).

**Процесс ведения:**

- Любой инцидент в проде → новый кейс в golden set.
- Регулярный аудит: устаревшие кейсы убираются (например, изменился регламент).

## Q5. Регрессионный прогон — как устроен?

**В CI:**

1. PR меняет промпт / схему / tools / модель.
2. Pipeline прогоняет golden set (по сэмплированию: критичные — 100%, остальные — стратифицированный сэмпл).
3. Считает метрики, сравнивает с baseline.
4. Блокирует merge, если: faithfulness упал > 2%, refusal_rate изменился > 5pp, latency p95 вырос > 20%, любая критическая категория уронила метрику.
5. Output — отчёт с diff'ом по кейсам: «вот эти 7 кейсов теперь дают другой ответ».

**Стоимость:** прогон может стоить десятки/сотни долларов на запуск. Поэтому — стратификация и кеширование на одинаковых промптах.

## Q6. Как мониторить стабильность в проде?

**Дашборды (минимум):**

- Объём и распределение запросов по интентам.
- Refusal rate, escalation rate.
- Latency p50/p95/p99.
- Cost per request, cost per resolved.
- Faithfulness и answer relevance на сэмпле (LLM-as-judge раз в час/день).
- Policy violations.
- Tool error rates по каждому tool.

**Алерты:**

- Резкий рост refusal или escalation.
- Падение faithfulness.
- Рост latency / cost (часто сигнал, что промпт начал «уходить» в длинные ответы).
- Дрейф распределения тем — может быть признаком атаки или реального инцидента у клиентов.

## Q7. Как сравнивать две модели (например, при апгрейде)?

**Процедура:**

1. Прогон обеих на одинаковом golden set.
2. Pairwise blind judge (LLM или человек): A vs B без знания, какая из моделей где.
3. Расчёт win-rate, по категориям отдельно.
4. Анализ кейсов, где новая хуже старой — часто это специфика формата вывода (новая модель «болтливее» или строже к refusal).
5. **Cost / latency** — отдельным измерением.
6. Решение: rollout / iterate на промпте под новую / отказ.

## Q8. Когда метрики «врут»?

**Типичные ловушки:**

- Высокая faithfulness, но низкая полезность — ответы цитатные, но не отвечают по сути.
- Низкий refusal rate выглядит хорошо, но скрывает галлюцинации.
- Высокий thumb-up, но низкий resolution — клиенты благодарят и идут к оператору.
- Хорошие offline-метрики, плохой prod — golden set не отражает реальный трафик.

**Лечение:** **корзина метрик**, не одна метрика; регулярная сверка offline/online; обновление golden set от прод-логов.

## Q9. Как считать стоимость и оптимизировать?

**Слагаемые:**

- Tokens in × price.
- Tokens out × price.
- Embedding calls × price.
- Reranker calls × price.
- Vector DB storage / queries.
- Compute для on-prem моделей.

**Оптимизации (в порядке приоритета):**

1. **Сжать system prompt** — он повторяется в каждом запросе.
2. **Кешировать** часто повторяющиеся ответы (FAQ).
3. **Prompt caching** провайдера (`Anthropic`, `OpenAI` — кеш system prompt'а).
4. **Меньшая модель для простых задач**, большая — только когда нужно.
5. **Сократить top-k** в RAG, если reranker качественный.
6. **Streaming** для UX, чтобы не ждать полный ответ.

## Q10. Метрики, специфичные для банка

- **PII leak rate** — должно быть 0; алерт при любом случае.
- **Off-topic rate** — доля ответов вне домена.
- **Compliance citation rate** — доля ответов на регламенты, где правильно процитирован источник.
- **Outdated info rate** — доля ответов на основе устаревших документов (тестируется на специальном fresh-наборе).

## Шпаргалка терминов

| Термин | Краткое определение |
|--------|---------------------|
| Faithfulness | Соответствие ответа предоставленному контексту |
| Groundedness | То же — наличие оснований в источниках |
| Answer relevance | Отвечает ли ответ на вопрос |
| Refusal rate | Доля отказов модели |
| LLM-as-judge | Оценка ответов другой LLM по rubric |
| Pairwise eval | Сравнение «A vs B» вместо абсолютной оценки |
| Golden set | Эталонный набор кейсов |
| Regression suite | Автоматический прогон при изменениях |
| Cohen's kappa | Метрика согласия между судьями |
| A/B test | Сравнение двух вариантов на трафике |
