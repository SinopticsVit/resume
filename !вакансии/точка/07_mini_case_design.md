# 07 · Мини-кейс системного дизайна

## Постановка кейса (вероятный сценарий на интервью)

> Клиент банка задаёт ассистенту вопрос: «Как мне правильно оформить операцию X / документ Y?». У вас есть внутренняя wiki с регламентами и API статуса операций клиента. Спроектируйте MVP за 2–3 спринта. На что обратите внимание?

## Структура ответа на 10 минут

Я отвечаю по структуре: **use cases → политика безопасности → архитектура → метрики → пилот → мониторинг**. Явно проговариваю, что **НЕ делает** ассистент в v1.

### Шаг 1. Уточняющие вопросы (важно задать первым делом)

- Кто пользователь: бухгалтер компании-клиента или конечный физик?
- Какие классы запросов в scope v1? Только FAQ или операции тоже?
- Есть ли существующая база знаний? В каком формате?
- Какие гарантии нужны: какой допустимый процент эскалаций? Какая цена ошибки?
- Есть ли требование «всё on-prem»? Какой LLM-провайдер уже одобрен?
- Какие SLA по latency и стоимости?

**Зачем задавать:** показывает product-thinking; ответы определяют архитектуру.

### Шаг 2. Use cases v1 (что делаем) и не-цели (что НЕ делаем)

**В scope v1:**
- Ответы на вопросы из регламентов (RAG по wiki).
- Получение статуса операции через read-only tool `get_operation_status`.
- Эскалация на оператора по триггерам.

**НЕ в scope v1 (явно):**
- Инициация платежей, переводов, изменений данных клиента.
- Налоговые консультации (требуют лицензии).
- Юридические заключения.
- Выдача персональных рекомендаций по инвестициям.

**Почему явно:** в банке cost ошибки высока; v1 должен быть «безопасный по конструкции».

### Шаг 3. Политика безопасности (до архитектуры)

- **PII**: в контекст модели — только минимально необходимое. Полные данные — в tool-результатах с маскированием.
- **Provider**: для PII-задач — on-prem или RU-region модель; для классификации без ПД допустим внешний.
- **Prompt injection**: разделение ролей в промпте, allowlist tools, DLP на выходе.
- **Refusal политика**: если в KB нет ответа — корректный отказ + эскалация. Никаких догадок.
- **Audit**: каждый запрос → trace с `prompt_version`, `model`, `retrieved_doc_ids`, `outcome`.

### Шаг 4. Архитектура

```
[UI / мессенджер]
        │
        ▼
[API Gateway: auth, rate limit, session]
        │
        ▼
[Orchestrator]
   ├─→ Intent classifier (быстрая small model)
   ├─→ RAG retrieval (hybrid: vector + BM25 + reranker)
   ├─→ Tool registry (read-only в v1: get_operation_status)
   ├─→ LLM (с structured output)
   ├─→ Output validator (citations required, DLP, schema)
   └─→ Эскалация на оператора (триггеры)
        │
        ▼
[Логирование / Tracing] → [Dashboards / Alerts]
        │
        ▼
[Eval pipeline: golden set, regression, LLM-as-judge]
```

**Компоненты:**

- **Vector DB**: `pgvector` для старта (минимум инфры), Qdrant если нужен hybrid из коробки и масштаб.
- **Эмбеддер**: мультиязычный (`bge-m3` или аналог), on-prem.
- **LLM**: одна сильная модель + одна маленькая для классификации.
- **Кэш**: Redis для частых FAQ.
- **Logging**: OpenTelemetry-совместимое решение, `Langfuse`/`Phoenix` для LLM-трейсов.

### Шаг 5. Промпт-архитектура

- **System**: роль, scope, отказная политика, формат вывода.
- **Developer**: brand voice, специфика (бухгалтер / селлер), список разрешённых tools.
- **Context block**: RAG-сниппеты с метаданными в `<knowledge_base_snippet>` тегах.
- **User**: запрос пользователя в `<user_input>`.
- **Output schema**: `answer`, `citations[]`, `confidence`, `needs_human_review`, `refusal`.

### Шаг 6. Метрики и пороги для запуска пилота

**Минимум для запуска:**
- Faithfulness ≥ 90% на golden set (50+ кейсов).
- PII leak rate = 0% на adversarial test.
- Refusal rate в диапазоне 5–20% (определяем с продуктом).
- p95 latency < 5 сек.
- Cost per query в бюджете.

**Online (на пилоте):**
- Resolution rate (без эскалации).
- CSAT.
- Repeat question rate.
- Алерты на drift.

### Шаг 7. План на 2–3 спринта

**Спринт 1 (2 недели): фундамент**
- Discovery, требования, threat model.
- Сбор golden set (30–50 кейсов от продукта).
- Ingestion pipeline для wiki: парсинг, chunking, эмбеддинги.
- Базовый RAG с hybrid search.
- Скелет API + auth + logging.

**Спринт 2 (2 недели): качество и безопасность**
- Промпт + structured output + citations.
- Output validator + DLP.
- Tool `get_operation_status` (read-only).
- Регрессионный прогон в CI.
- Дашборд: latency, cost, refusal, faithfulness.

**Спринт 3 (2 недели): пилот**
- Closed alpha на 5–10 внутренних пользователях.
- Сбор фидбека, разметка плохих кейсов.
- Итерация промпта и KB.
- Подготовка к расширению: документация, runbook.

### Шаг 8. Что мониторим в проде

- Объём, распределение интентов.
- Faithfulness и refusal rate на сэмпле (LLM-as-judge раз в час).
- Tool error rates.
- Latency, cost.
- Policy violations (DLP-флаги).
- PII leak attempts.

### Шаг 9. Что готовим к v2

- Расширение scope (write-tools с подтверждением).
- Multi-language если нужно.
- Persona switch (бухгалтер ↔ селлер).
- Голос / мультимодальность.
- Самообслуживание контент-команды (загрузка документов в KB).

## Кейс-вариация: «Ассистент уже есть, надо улучшить качество»

Если кейс другой («у нас работает, но качество среднее»), структура ответа:

1. **Diagnose**: какие метрики проседают? Это retrieval, generation или политика?
2. **Instrument**: дашборды, sample inspection, разметка 100 случайных кейсов.
3. **Hypothesize**: топ-3 причины с приоритетом.
4. **Experiment**: один эксперимент — одна гипотеза, A/B.
5. **Iterate**: победителя в прод, цикл повторяется.

## Кейс-вариация: «Расскажи, как бы ты улучшил наш ассистент бухгалтера»

Можно ответить так:

> «Не зная деталей внутренней архитектуры, я бы пошёл по такой логике. Сначала разметил бы 100 случайных диалогов и нашёл топ-3 проблемы — это обычно либо плохой retrieval по специфическим терминам (коды документов, номера статей), либо галлюцинации на пограничных вопросах, либо отказы там, где ответ был возможен. Под каждую гипотезу — конкретное действие: hybrid search с BM25 для точных терминов, faithfulness-валидатор с citations для галлюцинаций, расширение KB под белые пятна. Параллельно — построение регрессионного прогона, чтобы любая будущая правка промпта не ломала текущие сценарии. Это всё, что я бы сделал в первый месяц. Конкретные приоритеты — после знакомства с реальным трафиком и метриками».

## Что НЕ говорить в кейсе

- «Возьмём GPT-5 и подключим к wiki» — без архитектурной глубины.
- «Сделаем multi-agent на 10 агентов» — переусложнение для FAQ.
- Конкретные обещания по метрикам Точки.
- «У вас плохо сделано, я бы переделал всё» — нет уважения к команде.
