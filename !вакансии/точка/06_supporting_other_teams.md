# 06 · Сопровождение продуктовых команд

В вакансии прямо: «Сопровождать внутренние команды внедрения: проводить архитектурные ревью, писать гайды, участвовать в обучении и развитии сообщества». Это треть роли.

## Q1. Как вы работаете с командой, которая впервые подключает LLM?

**Мой подход — три встречи + артефакты:**

1. **Discovery (1 час):**
   - Какая бизнес-задача? Кто пользователь? Какова цена ошибки?
   - Какие данные есть? Где они лежат? Кто owner?
   - Какие гарантии нужны (точность / полнота / latency / cost)?
   - Что уже пробовали?

2. **Architecture review (1–2 часа):**
   - Разбираем предложенную архитектуру по чеклисту (см. Q4).
   - Проходим по threat model: PII, prompt injection, эскалация.
   - Согласуем метрики качества и порог запуска.
   - Выдаём список рисков с приоритетом.

3. **Pilot review (после первой версии):**
   - Смотрим на реальные кейсы и метрики.
   - Помогаем отстроить evaluation pipeline.
   - Передаём support команды на самостоятельную работу.

**Артефакты, которые остаются у команды:**
- Заполненный template архитектуры.
- Список рисков и митigations.
- Golden set (минимум 30 кейсов, собранных совместно).
- Инструкция по логированию и мониторингу.

## Q2. Как пишете гайды для разработчиков?

**Принципы хорошего внутреннего гайда:**

- **Use case first**: «Если ты делаешь X, начинай отсюда». Не «вот теория embeddings».
- **Cookbook-стиль**: рабочие примеры кода, копипаст-готовые промпты, схемы пайплайна.
- **Anti-patterns** наравне с patterns: что НЕ делать, чем это пахнет в проде.
- **Versioned**: гайд имеет дату и владельца, устаревшие куски помечаются.
- **Diataxis-разметка**: tutorials / how-to / reference / explanation — каждый тип решает свою задачу.
- **Минимум воды**: после прочтения должно быть понятно, что делать в понедельник утром.

**Темы гайдов, которые я бы написал в первый месяц:**
- «Как добавить LLM-фичу к вашему сервису» (templates, code samples).
- «Как собрать golden set за один день».
- «Чеклист безопасности для LLM-фичи».
- «Как читать логи LLM-инцидента».
- «RAG в нашей инфраструктуре: outline».
- «Версионирование промптов: правила команды».

## Q3. Что смотрите на архитектурном ревью LLM-фичи?

**Чеклист:**

### Функциональные
- Use case чётко сформулирован: вход / выход / ограничения.
- Критерии успеха измеримы (метрики).
- Что делает фича в **failure mode** (LLM отказала, tool упал, KB пустая).

### Данные
- Где источники, кто owner, как обновляются.
- Чувствительность данных, access control.
- Минимизация контекста.

### Архитектура
- Промпт хранится как код, не в строке.
- Structured output, валидация.
- Function calling: список tools минимален и обоснован.
- Идемпотентность для write-операций.
- Эскалация на человека предусмотрена.

### Безопасность
- Threat model (prompt injection, PII leakage).
- DLP на выходе.
- Логирование с маскированием.
- Kill switch.

### Качество
- Golden set есть до выкатки.
- Регрессионный прогон в CI.
- Метрики и алерты.

### Эксплуатация
- Cost / latency budgets зафиксированы.
- Observability: trace_id, dashboards.
- Runbook для инцидентов.

### Эволюция
- Как меняется промпт без даунтайма.
- Как апгрейдится модель.

## Q4. Как развиваете сообщество?

**Конкретные форматы:**

- **Brown bag / митапы** раз в 2–4 недели: 30 минут разбор кейса (наш или внешний), 30 минут вопросов.
- **Внутренний канал** в мессенджере: новости LLM, шеринг best practices, разбор инцидентов (анонимизированно).
- **Office hours** — час в неделю, любой инженер может прийти с вопросом по LLM-фиче.
- **Library of patterns** — внутренний репозиторий с готовыми шаблонами (RAG, agent, classifier, summarizer).
- **Reading group** — раз в месяц разбор статьи или нового релиза модели.
- **Postmortems** инцидентов LLM-фич распространяются по сообществу.

## Q5. Как балансируете «помочь» и «не делать вместо»?

- **Сильный консультант объясняет, как сделать самим**, а не пишет код за команду.
- **Парное программирование** на старте — 1–2 дня, дальше команда летит сама.
- **Чеклисты и шаблоны** дают структуру, но команда заполняет своими данными.
- **Эскалация ко мне** — только если команда уже попробовала и упёрлась; иначе обкрадываю их рост.

## Q6. Как обрабатываете конфликт «продукт хочет быстрее, я говорю медленнее ради качества»?

**Подход:**

- Не «нет, нельзя» — а **«риск + цена + альтернатива»**.
- Перевожу разговор в плоскость метрик: «При текущем уровне faithfulness 82% мы получим N жалоб в неделю. Готовы?»
- Предлагаю **MVP с уменьшенным scope** вместо отсрочки: «Запустим только FAQ, без операций. Через 2 недели расширим».
- Договариваемся о **stop-criteria для пилота**: если метрика X упадёт ниже Y — откатываем без обсуждения.
- Документирую решение, кто его принял и на каких данных.

## Q7. Как менторите junior-инженера?

- **Стартовые задачи** с понятным success criteria.
- **Парное программирование** на первом RAG / agent проекте.
- **Reading list** из 5–10 ключевых ресурсов.
- **Регулярная обратная связь**: 1:1 раз в 1–2 недели.
- **Делегирование с правом ошибки**: даю задачи, где провал не смертелен, но обучает.

## Q8. Что считаете признаком зрелой LLM-команды?

- Промпты в git, изменения через PR.
- Каждый инцидент порождает кейс в golden set.
- Метрики выкатки видят все, не только автор.
- Любой инженер может запустить регрессионный прогон.
- Postmortems публичны (внутри компании).
- Гайды живые и актуальные.
- Сообщество шерит знание без «дворцовых» барьеров.

## Шпаргалка терминов

| Термин | Краткое определение |
|--------|---------------------|
| Architecture review | Структурированный разбор архитектуры до выкатки |
| Diataxis | Фреймворк документации (tutorial / how-to / reference / explanation) |
| Cookbook | Стиль документации с готовыми рецептами |
| Office hours | Открытое время для вопросов от других команд |
| Postmortem | Разбор инцидента без виноватых |
| Brown bag | Неформальный митап (часто за обедом) |
