# 03 · Tools, function calling и агенты

## Q1. Что такое function calling и зачем он ассистенту банка?

**Короткий ответ:** function calling — это механизм, при котором LLM по контексту выбирает один из заранее описанных инструментов (с JSON-схемой) и возвращает структурированный вызов. Сам код инструмента выполняет наша система, не модель.

**Зачем в банке:**

- Достать **точные данные** (баланс, статус операции, реквизиты) — модель не должна угадывать цифры.
- Выполнить **действие** (создать заявку, открыть тикет, переслать оператору).
- Поиск по KB — это тоже tool (`search_knowledge_base(query, audience)`).
- Чёткая граница «модель решает что сделать — код решает можно ли это сделать».

## Q2. Как описывать tools правильно?

**Принципы:**

- **Минимум инструментов** в одном промпте — каждый лишний tool увеличивает шанс ошибочного выбора. Эмпирика: 5–10 tools хорошо, 30 — уже плохо. При большом наборе — иерархия (router agent → специализированные).
- **Однозначное имя**: `get_account_balance`, не `get_data`.
- **Подробный `description`**: что делает, когда применять, когда НЕ применять, какие side effects.
- **Чёткая схема параметров** (JSON Schema): обязательные поля, enums, regex-валидация.
- **Идемпотентность**: tools, меняющие состояние, должны принимать `idempotency_key`.
- **Read-only по умолчанию**: write-операции — отдельный класс с подтверждением.

**Пример:**

```json
{
  "name": "search_knowledge_base",
  "description": "Searches internal banking knowledge base for regulations and FAQs. Use when user asks about banking rules, fees, procedures. Do NOT use for user's personal account data.",
  "parameters": {
    "type": "object",
    "properties": {
      "query": {"type": "string"},
      "audience": {"type": "string", "enum": ["accountant", "seller"]},
      "top_k": {"type": "integer", "minimum": 1, "maximum": 10, "default": 5}
    },
    "required": ["query", "audience"]
  }
}
```

## Q3. Как контролировать цикл вызова tools?

**Обязательные ограничения:**

- **`max_steps`** — например, 6–10 итераций tool→model→tool. Превышение → forced final answer или эскалация.
- **`max_total_tokens`** — бюджет на сессию.
- **`timeout`** — на каждый tool и на всю цепочку.
- **`max_parallel_tools`** — если разрешены параллельные вызовы.
- **`forbidden_sequences`** — например, нельзя вызывать `transfer_money` без `verify_user`.
- **Allowlist tools per intent**: ассистент бухгалтера не имеет доступа к tools селлера.
- **Kill switch**: глобальный флаг отключения write-tools (для инцидентов).

## Q4. Когда нужен агент, а когда хватит одного вызова?

**Эвристика:**

- **Single-shot LLM**: вопрос — ответ из KB. Простые FAQ, объяснения регламентов.
- **One tool call**: нужно достать одну цифру/факт (баланс, статус документа).
- **Tool loop (ReAct-стиль)**: задача из 2–4 шагов, заранее не известно, какие данные понадобятся.
- **Multi-agent**: задача требует **разной экспертизы** или **параллельной обработки** разных аспектов одного объекта (например, проверка контрагента: юрист, финансы, логистика — каждый со своей логикой и набором tools).

**Антипаттерн:** делать multi-agent там, где хватает одного промпта с несколькими tools. Это удорожает токены, латентность и отладку.

## Q5. Multi-agent — когда оправдан?

**Когда оправдан:**

- Параллельные ветки с независимыми входами и выходами.
- Разделение ответственности: каждый агент имеет свой системный промпт, свой allowlist tools, свои метрики.
- Нужен оркестратор-агент (planner/router) который собирает финальный ответ.

**Пример из моего опыта** (Dify-workflow, см. `eqvilent_trading_analytics_prep_RU.md`): 24 ноды, 5 параллельных агентов (Lawyer, Logistics, Finance, Marketing, Accounting) на проверке контрагента; orchestrator собирает validation report. Это аналог n8n/Make/Workato с LLM-нодами.

**Когда multi-agent не оправдан:**

- Линейный pipeline без ветвления.
- Если разные «агенты» отличаются только промптом — это один агент с разными ролями.
- Если отладка важнее скорости разработки — каждый дополнительный агент удваивает количество failure modes.

## Q6. Чем отличаются ReAct, Plan-and-Execute, Router?

**ReAct (Reasoning + Acting):** модель чередует thoughts и actions, на каждом шаге решает, что делать дальше. Гибко, но непредсказуемо по числу шагов.

**Plan-and-Execute:** сначала планировщик (LLM) строит явный план шагов, потом исполнитель идёт по плану. Лучше для предсказуемости и аудита; легче проверять «безопасность плана» до исполнения.

**Router (Intent classification):** первый LLM классифицирует запрос и направляет на специализированного агента / промпт. Хорошо, когда классов запросов мало и они чётко различимы.

**Мой подход для банка:** для критичных действий — **Plan-and-Execute с явным approval-шагом** перед write-операциями. Для FAQ — Router → специализированный агент с RAG.

## Q7. Как проектировать «эскалацию на человека»?

**Триггеры эскалации:**

- `confidence < threshold`.
- `refusal` от модели по политике.
- Превышение `max_steps` без финального ответа.
- Тема в `escalation_topics` (жалобы, споры, потери).
- Пользователь явно попросил оператора.

**Что передавать оператору:**

- Краткая саммари диалога (LLM-сжатие).
- История вызовов tools и их результаты.
- Документы, которые ассистент использовал.
- Метаданные: `prompt_version`, `model_version`, `session_id`.

## Q8. MCP (Model Context Protocol) — что это и где применимо?

- MCP — стандартизованный протокол для подключения tools/контекста к LLM-агентам, разделяет «что предоставляет данные» и «что их использует».
- Полезен, когда у компании много внутренних сервисов и нужно унифицировать их подключение к разным агентам.
- Я использую MCP в SinopticsAI для расширения возможностей продукта — это упоминал в резюме.
- В Точке упомянут «опыт работы с MCP» как плюс — можно сослаться на этот опыт.

## Q9. Параллельные tool calls — за и против

**За:** скорость (несколько независимых данных параллельно), меньше токенов на лишние раунды.

**Против:** сложнее отлаживать, риск race conditions, лимиты у внешних API.

**Правило:** разрешать параллельные вызовы только для **read-only** tools и при явной независимости. Write-tools — строго последовательно.

## Q10. Observability агентских пайплайнов

**Что логировать на каждый шаг:**

- `trace_id`, `session_id`, `step_id`.
- `prompt_version`, `model`, `temperature`.
- `tool_called`, `tool_args`, `tool_result_size` (без PII).
- `tokens_in/out`, `latency_ms`, `cost`.
- `decision_reason` (если есть structured output с reasoning-полем).
- На финальном шаге — `final_answer`, `citations`, `outcome` (success / refusal / escalation).

**Инструменты:** `Langfuse`, `Helicone`, `Phoenix` (Arize), OpenTelemetry-совместимые трейсы. На интервью могу сказать «не привязан к конкретному инструменту, важна сама дисциплина трассировки».

## Шпаргалка терминов

| Термин | Краткое определение |
|--------|---------------------|
| Function/tool calling | Структурированный вызов внешней функции по решению LLM |
| Agent | LLM в цикле tool→reasoning→tool с целью |
| ReAct | Reasoning + Acting в одном цикле |
| Plan-and-Execute | Сначала план, потом исполнение |
| Router | Классификатор намерений → специализированный агент |
| Multi-agent | Несколько агентов с разной ролью + оркестратор |
| MCP | Model Context Protocol — стандарт подключения tools/контекста |
| Idempotency key | Ключ, гарантирующий безопасность повторного вызова |
| Trace | Цепочка событий одного запроса для observability |
