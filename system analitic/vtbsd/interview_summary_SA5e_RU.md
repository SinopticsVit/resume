## 5. Архитектура: три параллельных компонента

```
[Клиент: организация / УК, много пользователей]
   ├─ Web ЛК ── входящие / исходящие / черновики / редактор полей
   └─ Шлюз (on-prem у клиента) ── watch папок ↔ файлы + метаданные
              │
              ▼
        [Сервер ЭДО] ── документы, маршруты, кому/от кого
              │
              ▼
   Ответы «офиса» → и в ЛК, и в папки шлюза
```

### 5.1. Сервер (backend)

- «Машинка» обработки всего, что связано с **документами и маршрутами**.
- Приём, маршрутизация, кому отправить / от кого принять — ядро документооборота.

### 5.2. Web / личный кабинет

- Веб (backend упоминался как **Java**), классический UI ЭДО.
- Входящие, исходящие, черновики и пр.
- Редактор: заполнение документов по полям (не только файлы).

### 5.3. Шлюз (ключевой акцент Максима)

- Ставится **у клиента** (организация; пользователей может быть много, пример — порядка 20).
- **Не** шина «между блоками фронта», а канал обмена организации с сервером.
- ~90% пользователей хотят **просто отправлять файлы** (не сидеть в веб-форме).
- Поведение: джоба/сервис смотрит папки, забирает документы + сопроводительные метаданные/таблицы «куда что», отправляет на сервер (в т.ч. с подписью/обработкой), принимает ответные файлы во **входящие** папки.
- Шлюз **двусторонний**: не только send, но и receive; постоянный контакт/опрос.
- Параллельная разработка трёх компонентов — отдельная сложность для синхронизации модели документа и статусов.

### SQL / данные / кейс импорта (отработано в ветке подготовки)

Ниже — зафиксированные формулировки после разбора ответов кандидата (реляционные vs NoSQL, JOIN, кейс импорта разнородных отчётов). Готовые устные скрипты также в `prep_interview_VTBSD_RU.md` §D / кейс импорта.

**Реляционные vs нереляционные БД**

- Реляционные: жёсткая схема (таблицы, колонки, типы), PK/FK, уникальные/не уникальные ключи, индексы, SQL; типично сильные гарантии целостности и транзакций (ACID).
- NoSQL (MongoDB — документы/JSON; Neo4j — графы): **гибкая / нефиксированная** схема (не «нечёткая»): у разных записей набор полей может отличаться; индексы тоже бывают; целостность чаще на стороне приложения.
- Не говорить «транзитивность» — если усиливать ответ: про **транзакции** и ссылочную целостность.
- Мост к ЭДО/учёту: учёт и юр.-значимый обмен обычно на реляционной модели; NoSQL — гибкие события/логи/документный доступ (у кандидата был PostgreSQL + Mongo).

**INNER JOIN vs OUTER JOIN**

- INNER — только строки с совпадением ключа в обеих таблицах (пересечение).
- LEFT OUTER (на практике чаще «LEFT JOIN») — все строки слева; без пары справа → `NULL`.
- RIGHT / FULL — зеркало и объединение обеих сторон; в работе реже.
- Пример для приёмки: INNER = документы с логом; LEFT = все документы, в т.ч. без ответа интеграции (`result IS NULL`).

**Кейс: импорт разнородных отчётов (у каждого источника своя структура) в целевую модель**

Порядок анализа СА (не сразу «писать импорт»):

1. Границы: что, от кого, куда, частота, критерий успеха.
2. Контракт источника: форматы, версии, обязательные поля; каталог отличий по брокерам/источникам.
3. Целевая модель: сущности, обязательные поля, ключ идемпотентности, статусы приёмки.
4. Маппинг + валидации + справочники; поведение на неизвестных кодах.
5. Процесс: ручной/по расписанию, отчёт об ошибках, перезаливка, аудит.
6. Артефакты: as-is/to-be, матрица маппинга, 5–7 критериев приёмки (happy path, битый файл, дубликат, новая версия формата).
7. Архитектурный выбор при разных структурах: профиль на источник **или** нормализация в канонический промежуточный формат → целевая БД.

### Идемпотентность (отработано в ветке подготовки)

Готовый устный скрипт также в `prep_interview_VTBSD_RU.md` §C.

**Определение:** свойство операции — повторный вызов с теми же данными даёт тот же результат и не создаёт побочный эффект второй раз (сеть/таймаут/ретрай не проводят операцию дважды).

| Операция | Идемпотентна? |
|----------|----------------|
| `GET /documents/123` | Да — сколько ни читай, документ один |
| `PUT` «статус = SIGNED» | Обычно да — повтор не меняет итог |
| `POST` «создать платёж» без ключа | Нет — каждый вызов может создать новый |
| Повтор ЭД с тем же `messageId` / business key | Да — если заложен ключ и статус «уже обработан» |

**Устно (~30 сек):**  
«Идемпотентность — защита от дублей при ретраях. В контракте фиксируем ключ идемпотентности или id документа; при повторной доставке не создаём вторую проводку, а возвращаем текущий статус обработки».

**Мост к продукту Максима:** особенно критично для **файлового шлюза** (повторная выкладка файла в папку) и единого статуса на сервере для ЛК и шлюза.
